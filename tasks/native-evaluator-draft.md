# 可复用原生评估模块草稿

状态：用户已于2026-11-15授权按此草稿开始实施；实现入口见[原生评估模块](../experiments/native_eval/README.md)，实际通过范围与边界见其[验证记录](../experiments/native_eval/VALIDATION.md)。目标是在明确支持范围内复用MuJoCo评估执行，同时保留整段原生热循环的性能。当前固定模型实验是正确性/性能基线，不是生产接口规格。

## 模块与接口

外部接口保持小：用任务描述、策略产物与评估选项建立评估器，再以一组初始状态执行评估并返回统一结果。训练与网页调用者无需了解内部物理子步、内存布局或线程调度。

| 模块 | 负责什么 | 变化从哪里进入 |
| --- | --- | --- |
| 通用评估执行模块 | 模型/资源生命周期、批量环境、物理与控制周期调度、首回合mask、终止/截断/重置、计时和结果归集 | 环境数、时长、种子等运行选项（当前单原生控制线程） |
| 策略适配 | 已声明支持的模型产物载入、输入归一化、推理与输出变换 | 模型形状、激活、归一化、策略头及格式版本 |
| 任务适配 | 观测构造、动作单位/映射、控制状态、奖励、有效性和终止判断 | 任务原生实现及任务参数 |

MuJoCo XML及其资源由任务描述指定。关节/执行器名称在建立任务时解析并缓存，核心不认识腿、轮或本项目的数组索引。当前残差轮扭矩头、J*F几何与奖励公式属于适配内容。

原生接口一次执行完整评估批次。任务适配在原生热循环内运行，避免为每个控制周期/物理子步跨回Python。Python负责配置、模型产物、启动取消和展示结果；实现方式可采用原生任务注册等简单机制，暂不预设动态插件系统或奖励DSL。

## 配置与支持范围

- 检查点位置、模型输入/输出尺寸、批量数、评估时长、控制/物理步长都由输入或模型描述提供。当前24维、4执行器、8环境、600控制步与四物理子步仅是基准用例。
- 策略适配明确支持的格式、算子和输出头，拒绝不支持的产物；当前MLP基线不自动代表任意网络均可加载。
- 任务参数包括奖励权重、动作尺度、关节映射及控制历史。相同任务更换已支持模型或参数时，无需改核心；新任务可以增加一个任务适配。
- 任务描述写清观测/动作单位、频率、参数版本，以及终止与时间截断语义。任务适配负责保留按物理子步更新的控制逻辑；核心按配置调度，不写死四子步。
- 模型校验、配置冲突与能力检查在建立阶段完成。尚未支持的随机化、网络或控制时序给出明确错误，不隐式退回另一套语义。
- 评估结果统一返回各环境首回合长度、累计回报、终止/截断原因、耗时及可选诊断；调试轨迹可按需开启。内部实现变化不会要求网页重新理解统计口径。

## 实现前验收门槛

1. 当前腿力＋轮扭矩基线继续通过同模型CPU/GPU动作、一步物理、回报、轨迹与终止对照。
2. 再接一种现有不同控制语义，例如腿位置＋轮扭矩，核心执行模块无需修改；更换检查点、网络尺寸、环境数与评估时长同样不改核心。
3. 用一种不同nq/nu和观测维数的简单MuJoCo任务，例如单摆，证明任务接入只增加描述/适配及对应验证，没有轮腿假设泄漏进核心。无需为此训练新策略。
4. 覆盖提前终止、正常时间截断、重置后历史状态、不同种子、批量大小和控制子步数。当前全部600步标称成功不能替代这些用例。
5. 每种适配各自验证数值一致性与性能；分别记录载入、预热与持续评估。通用化后仍需用数据证明收益，不能沿用单任务热点比例作为加速承诺。

当前`tasks/results/cpu-gpu-eval/native_cpu_eval.py`是有意限制于单一标称条件的基准适配器，包含固定8环境等断言，仅用于这次公平比较。它不满足以上生产验收门槛，也不应直接提升为通用实现。
