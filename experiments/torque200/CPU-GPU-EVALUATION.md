# 同模型原生CPU与MJX GPU评估（2026-11-15）

结论：当前零命令标称场景通过预设一致性门槛。预热后原生CPU评估中位4.117秒，现有GPU评估中位3.938秒，CPU约慢4.5%，没有得到持续评估加速；CPU首次调用明显省去了GPU编译等待。保持现有GPU评估，C++只考虑小范围闭环原型，优先处理几何/保护/扭矩更新和奖励统计，不据此开展全面重写。

- GPU计时直接调用生产使用的Brax `acting.Evaluator`及相同MuJoCo Playground包装；CPU使用原生MuJoCo＋现有NumPy ForcePolicy，串行执行8个真实环境。对照的是完整评估路径，包含推理、控制、物理、奖励与首回合统计，不是单独物理引擎测速。
- 原生回放原本没有完整训练奖励；隔离适配器复用生产奖励方法、将其数组后端绑定NumPy，并保留实际物理子步力矩的一/二阶历史惩罚及旧平衡参考的更新顺序。未修改生产奖励。
- 两边采用Brax一致的首回合统计顺序：done当步先计奖励/长度，再关闭累计mask。即使提前终止仍继续固定工作量并重置；本次实际均未提前终止，因此提前摔倒后的等价性没有得到动态覆盖。

计时使用单调时间并等待GPU完成；GPU与CPU测量顺序执行，速度测试没有同时运行两种评估。另行采集GPU诊断轨迹和CPU分段计时，不把其开销混进预热后速度表。没有训练、更新模型或改C++。

## C++边界

独立CPU诊断一次完成同样8×600工作量，共4.1558秒：

| 部分 | 秒 | 占诊断总量 |
| --- | ---: | ---: |
| 几何、保护、扭矩更新等控制外围，扣除mj_step | 2.0889 | 50.3% |
| 原生MuJoCo mj_step | 0.3816 | 9.2% |
| 奖励与实际扭矩历史统计 | 0.9682 | 23.3% |
| 观测构造 | 0.4925 | 11.9% |
| NumPy策略推理 | 0.1885 | 4.5% |

`mj_step`已经包含在原控制＋物理2.4704秒中，表中先扣除再拆开，没有重复加总。它是另一次带轻量计时包装的诊断，不替代前面的无诊断速度测试。外围部分同时包含Python、NumPy原生算子、数据访问和临时对象开销，不能笼统称为全部Python解释器耗时。

取舍：

1. 当前CPU路径没有预热后的速度收益，暂不替换生产GPU评估。
2. 值得考虑受限C++原型：将一个完整100Hz控制周期内四子步的几何、J*F映射、有效性/终止判断及扭矩历史合成一次原生调用；随后纳入观测与奖励统计，保留相同reset和首回合mask语义。当前控制外围与奖励合计约73.6%，比单改策略推理更有针对性。
3. 这只是热点范围，尚未测得C++加速倍数。原生物理本身已是C/C++实现；仅替换`mj_step`的Python调用形式覆盖不到主要开销。
4. 任一原型仍应重跑本次一致性合同，再补充提前终止、扰动、不同命令与更长时域；本次标称结果不能代替这些验收。
